The Numbers

Everything from lessons 0001–0010 worth holding in your head, and the syntax that isn't. Print this one too.

Companions: Reference 01 · Reference 03 · Reference 04 Updated 2026-09-03

Six things belong in memory. Everything below that line is lookup.

The six

Memorise these

1. Ease-out in, ease-in out. Entrances decelerate into place; exits accelerate away. An ease-out exit lingers at near-zero opacity, which is the worst place to spend time.

2. Exits run about half the entrance. 320ms in, 180ms out. The ratio that matters is 0.5–0.65. Nobody has ever complained a dismissal was too fast.

3. transform and opacity are free. Anything that changes geometry — width, height, top, margin, padding — costs Layout on every frame. If you can express the effect as a transform, do.

4. Overlap ≤ 0.35, and check the total separately. Two independent failures: the group can read as a queue, or it can simply take too long.

5. Reveals want a trigger, never a scrub. If the element carries meaning, its legibility must not depend on where the reader stopped scrolling.

6. Content must survive its own animation not running. Never hide something in a stylesheet that only JavaScript can unhide.

Durations that work

ThingEnterExit
Press feedback under a finger (0010)0–100ms~180ms
Hover, focus, small state change120–160mssame or less
The state change a press causes — toggle, checkbox150–200ms100–150ms
Dropdown, tooltip, popover180–250ms120–160ms
Modal, dialog, sheet280–360ms160–220ms
Full-screen or page transition400–500ms250–300ms
Hero entrance (per element)400–560ms—

The first row overrules the rest when it applies. Everything below it assumes the system moved first; a press answers a hand that already moved, and 0.1s is the limit for it still feeling like direct manipulation. The two press rows are different animations — the button yielding under the finger, and the checkbox filling in afterwards.

Ceiling: if a single element's animation exceeds ~500ms, it needs a reason. Above ~1s the reader thinks the page is broken, not elegant.

The two stagger equations

total = duration + (n − 1) × step

overlap = step ÷ duration

OverlapReads asVerdict
0Everything at onceA flash. No hierarchy.
≤ 0.35One gestureTarget.
0.35–0.8A visible waveOnly if the wave is the point.
> 1A queueEach finishes before the next starts. Wrong.

Keep total under ~800ms for a hero, ~500ms for a menu or list. More items means a smaller step, not a longer wait — budget the total first, then divide.

Lookup — don't memorise any of this

Scroll reveal, the whole pattern

<script>document.documentElement.classList.add('js');</script>

.js .reveal { opacity: 0; transform: translateY(20px); }
.reveal { transition: opacity 420ms var(--ease-out), transform 420ms var(--ease-out); }
.reveal.is-in { opacity: 1; transform: none; }

const io = new IntersectionObserver((entries) => {
  let batch = 0;
  for (const e of entries) {
    if (!e.isIntersecting) continue;
    e.target.style.transitionDelay = `${batch * 60}ms`;
    e.target.classList.add('is-in');
    batch += 1;
    io.unobserve(e.target);        // reveal once
  }
}, { rootMargin: '0px 0px -15% 0px', threshold: 0 });

The sign rule: negative bottom margin shrinks the root box upward and fires later. Positive grows it past the viewport and fires earlier. -15% is the working default.

Observe the container, not the items, when the group should read as one gesture — otherwise scroll speed decides your stagger for you.

Asymmetric enter/exit in pure CSS

.panel {                        /* resting state = the EXIT transition */
  display: none; opacity: 0; transform: translateY(10px);
  transition: opacity 160ms cubic-bezier(0.4,0,1,1),
              transform 160ms cubic-bezier(0.4,0,1,1),
              display 160ms allow-discrete;
}
.panel.open {                   /* active state = the ENTER transition */
  display: block; opacity: 1; transform: none;
  transition: opacity 340ms cubic-bezier(0.23,1,0.32,1),
              transform 340ms cubic-bezier(0.23,1,0.32,1),
              display 340ms allow-discrete;
}
@starting-style { .panel.open { opacity: 0; transform: translateY(10px); } }

A transition on a rule governs the journey to that rule. That is how you get two durations and two curves without any JavaScript.

The --i stagger

.item { transition-delay: calc(var(--i) * 60ms); }
<div class="item" style="--i: 0">…</div>

With animation-delay instead, you must add animation-fill-mode: backwards or the element flashes its final state first. transition-delay has no such problem.

Scroll-driven CSS (a scrub, not a trigger)

@supports (animation-timeline: view()) {
  .bar {
    animation: grow linear both;
    animation-timeline: view();
    animation-range: entry 10% cover 30%;
  }
}

Ranges: entry = crossing into view, cover = any part visible, exit = leaving. No duration — the range replaced it.

Hover and press, the whole shape

.btn {
  transition: transform 180ms var(--ease-out),   /* coming back up */
              background-color 140ms ease;
}

@media (hover: hover) {                          /* gate the hover — only the hover */
  .btn:hover { background: var(--accent-700); }
}

.btn:active {                                    /* outside the query: fingers press */
  transform: scale(0.96);
  transition: transform 80ms var(--ease-out);    /* going down */
}

.btn:focus-visible { outline: 2px solid var(--ink); outline-offset: 2px; }

Press depth from element width: edge displacement = (1 − scale) × width ÷ 2. Aim for 2–4px. 96px button → 0.96. 320px card → 0.985. Full-width → don't scale, darken.

Hover intent, no JavaScript: transition-delay: 300ms on the :hover rule, 0ms on the base rule. Waits on the way in, leaves immediately.

Debugging, in order

  1. Paint flashing (DevTools → Rendering). Green = repainted. A composited animation produces no green at all. Green during motion means it isn't composited.
  2. Layers panel. Flashing green and no layer of its own = confirmed non-composited animation.
  3. Performance recording. Purple is Layout, green is Paint. Long frames are the ones over 16.7ms.
  4. Click your toggle as fast as you can. If it queues, stutters or sticks, the motion isn't interruptible.
