Transform-origin, and where a menu comes from

One line of CSS, almost never written, that decides whether a popover looks attached to the button that opened it or merely lands nearby.

Skill: anchor a scaling element to the thing it came from ← Lesson 0006

A menu that appears near a button and a menu that comes out of a button are the same pixels, in a different order.

Every scale you've written so far has quietly used the default, transform-origin: 50% 50% — the element grows from its own centre, in all four directions at once. That default is right for exactly one situation, and popovers, menus, tooltips and dropdowns are not it.

This is a small lesson about a single property. It's here because it's the most common tell of amateur popover motion, it costs nothing to fix, and once you've seen it you cannot stop seeing it.

Try this, in order
  1. Hit Tour the corners and just watch for a few seconds. Both panels are identical except for one line.
  2. Now watch the small ring on each panel instead of the panel itself. That ring marks the transform-origin.
  3. Drag duration up to about 800ms so you can see it happening.
  4. Drag scale from down to 0.6, then up to 0.95, and watch the number under the sliders.

What you just saw

The ring never moves. That's not a trick of the demo — it's the definition. transform-origin is the fixed point of the transform: the one place on the element that scaling and rotation leave exactly where it was. Everything else moves relative to it.

So the question "where should this scale from?" is really the question "which point on this element must not move?" And for anything anchored to a trigger, the answer is obvious once you ask it that way: the corner touching the button. That corner is where the panel came from. If it moves, the panel didn't come from anywhere.

On the right-hand lane, the ring sits in the middle of the panel, so the anchored corner starts some distance away and travels in. At the default scale of 0.85 that's about 14px of travel — small enough that you'd never file a bug about it, large enough that the panel reads as sliding into place near the button rather than opening out of it. Most motion problems are this size.

The rule this gives you

Put the origin at the point the element came from.

For an anchored element that's the edge or corner nearest its trigger. For something that genuinely came from nowhere — a centred modal — the default centre is correct, and you should leave it alone deliberately rather than by accident.

transform-origin is free in the sense of lesson 0002: it changes the matrix the compositor applies, not which pipeline stages run. Setting it costs the same as not setting it. There is no performance argument for leaving it at the default — only inattention.

Picking the origin

The rule is a mirror. Whatever edge of the panel is pinned to the trigger, the origin goes on that edge.

Percentages and lengths work too, and are what you want when the trigger isn't at a corner — transform-origin: 24px 0 puts the fixed point 24px in from the panel's left edge, on its top edge, which is how you aim it at a button sitting somewhere in the middle of a toolbar.

Computing it, when the position isn't known in advance

A popover whose placement flips depending on available space can't have a hardcoded origin. Measure instead. This is a case where a couple of lines of JavaScript are the right tool — lesson 0006's ladder, question 1: it isn't two fixed states, it's a computed value.

function aimAt(panel, trigger) {
  const p = panel.getBoundingClientRect();
  const t = trigger.getBoundingClientRect();

  // The trigger's centre, expressed in the panel's own coordinate space.
  const x = (t.left + t.width  / 2) - p.left;
  const y = (t.top  + t.height / 2) - p.top;

  // Clamp to the panel's edges — an origin outside the box is legal but
  // reads as the panel being flung from off-screen.
  panel.style.transformOrigin =
    `${Math.max(0, Math.min(p.width, x))}px ${Math.max(0, Math.min(p.height, y))}px`;
}

Call it after the panel is positioned and before it animates. If you're using the Popover API, that means inside the beforetoggle handler.

CSS anchor positioning is starting to make the placement half of this declarative, and it exposes the resolved side to CSS — which will eventually let the origin be chosen without measuring. Support is still uneven; check MDN's anchor positioning page rather than trusting a number written here.

The whole thing, in pure CSS

Same checkbox pattern as lesson 0005, so the exit asymmetry comes along for free. The only new line is transform-origin — change it to center and watch the menu detach from its button.

It governs rotation too

Everything above was about scale, but the origin applies to the whole transform. Rotation is where it becomes physical: change the origin and you change what kind of object you're describing.

OriginA rotation reads as…
centerA dial, a spinner, a loading indicator
left centerA door, a hinge, a page turning
bottom centerA pendulum, a lever, something standing up
top centerSomething hanging — a tag, a pin, a dangling label

Turn on add a rotation in the lab and tour the corners again. The left-hand panel now reads as unfolding from the button. The right-hand one reads as a card someone tossed onto the screen. Same 8 degrees.

For SVG, percentages resolve against a different box by default, and transform-origin: center often won't do what you expect. Set transform-box: fill-box first and percentages start behaving like they do in HTML. See MDN on transform-box.

Two mistakes worth naming

Scaling from zero. Drag the lab's scale down to 0.2 and open it. The panel arrives as a magic trick, and on the way in the text is unreadable — genuinely unreadable, not just small, because the browser is rasterising type at a fraction of its size. Anchored elements want 0.85 to 0.95. The scale is a hint about where it came from, not a birth.

Origin on the wrong element. If your panel has a wrapper that also transforms, the origins compose and you'll chase the bug for twenty minutes. Put the scale and the origin on the same element, and let the wrapper handle position only.

When to leave it alone

Two cases, and they're both about honesty.

A centred modal didn't come from anywhere in particular — it's a mode change, not an expansion of a control. Centre origin, small scale, brief fade. Aiming it at the button that opened it would be a lie about the interface's structure, and it looks like one.

A toast or banner comes from an edge of the screen, not from a point on itself. That's a translate, not a scale, and the origin never enters into it. If you find yourself setting an origin on a toast, you've probably picked the wrong transform.

And for prefers-reduced-motion: the origin is the cheapest part to keep. Drop the scale to something tiny or remove it entirely and keep a short fade — but if you keep any scale at all, keep the correct origin. It's the part carrying the meaning.

What does transform-origin actually specify?

It's the fixed point. Scaling and rotation are defined relative to it, so everything else on the element moves and that point doesn't. Thinking of it as "which point must not move" is what makes the right value obvious.

A dropdown is pinned below a button on the right edge of a toolbar, with its right edges aligned. What origin?

Mirror the pinned edge. The panel touches the button along its top edge and is aligned to the right, so the top-right corner is the one that must not move. bottom right would be correct for a drop-up.

Your popover flips above the trigger when there's no room below. What has to happen to the origin?

The origin is relative to the panel's own box and knows nothing about the trigger. If the placement flips, the pinned edge flips, so the origin must flip too — which is exactly why dynamically placed popovers compute it rather than hardcoding it.

Why is scale(0.2) → scale(1) a poor entrance for a menu?

Scale is composited at any value, so cost isn't the issue. The problem is legibility and meaning: the scale is supposed to be a hint about where the panel came from. 0.85–0.95 gives you the hint without the circus.

Which of these should keep the default centre origin?

A centred dialog is a mode change; it isn't an expansion of any particular control, so it genuinely came from nowhere. The other two are anchored, and anchored elements should grow from the edge that touches their trigger.

Read this next

MDN's transform-origin is short and worth reading in full for the value syntax — keywords, percentages, lengths, and the third value for 3D. transform-box is the SVG footnote above, and will save you an afternoon eventually.

If you're building anchored things generally, CSS anchor positioning and position-area are where the placement half of this problem is heading, and getBoundingClientRect() is what the snippet above leans on.

Then go find a real dropdown — your own, or any site with an avatar menu — and watch its top corner. You now have a fast, reliable way to tell whether anyone thought about it.
