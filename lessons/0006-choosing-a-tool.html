Lesson 0006 · 20 minutes

Choosing a tool, and why it matters less than you think

Five lessons have name-dropped CSS, el.animate(), Motion and GSAP without ever telling you when to reach for which. Here's the decision rule, from first principles, in about six minutes of reading and one lab.

Skill: pick the cheapest tool that can do the job, and say why ← Lesson 0005

Libraries don't save you judgment. They save you plumbing.

Everything you've learned so far — ease-out in, ease-in out, exits at half, transform and opacity only, overlap under 0.35, reveals get a trigger — is tool-independent. Those are the decisions. A library can't make any of them for you, and picking the wrong one won't save a badly-timed animation.

So the question isn't "which tool is best." It's narrower and much easier to answer: what does this specific animation need to be able to do? Four things separate the tools, and you can feel all four in about ninety seconds.

Try this, in order
  1. Hit Play. All three lanes look identical. That's the point — for a plain one-shot animation, the tool genuinely doesn't matter.
  2. Hit Interrupt at 40% and watch lane 2 specifically.
  3. Hit Pause at 40% and watch lane 1 specifically.
  4. Hit Seek to 40% and read all three status lines.

What you just saw

Play is a tie. Three different technologies, one indistinguishable result. Most animation on most sites is exactly this: something changes, something moves, it's over. If that's your whole requirement, use the simplest thing that works and stop thinking about it.

Interrupt is where lane 2 falls apart. The transition eases back from wherever it had got to — 40-ish percent — because a transition interpolates from the current computed value, always. The keyframe animation snaps to zero, because a running @keyframes owns the property outright: take the animation away and the element is instantly wherever the base rule says it is. There is no "from here."

Pause flips the loser. Keyframes have animation-play-state: paused. Transitions have nothing — no pause, no scrub, no playhead of any kind. A transition is a one-way trip between two states that the browser is managing on your behalf, and you are not invited.

Seek is where the Web Animations API stops being optional. Lane 3 sets currentTime to a number and lands there. Lane 2 gets there with a negative animation-delay, which works and is a genuinely useful trick, but the moment you are computing negative delays to fake a playhead you have outgrown declarative CSS. Lane 1 can't participate at all.

The rule this gives you

A CSS transition is a rule about two states. A CSS keyframe animation is a recording you can start and stop. The Web Animations API is the same recording with a playhead you can hold.

Pick by what you need to hold onto.

The four real tools

Now the table is consolidation rather than introduction, because you've felt three of the four.

ToolReach for it whenCost
CSS transition Two states, and the user can change their mind. Hover, focus, open/closed, selected. Interruptible by default, which is why it's the right default for interactive UI. 0 KB
CSS keyframes Three or more steps, or it loops, or it runs on its own without a state change. A spinner, a pulse, a marquee, a page-load entrance. 0 KB
Web Animations API
el.animate()		 You need the playhead: pause, seek, reverse from here, read progress, know exactly when it's finished (.finished is a promise). Also when the keyframes themselves are computed at runtime. 0 KB
Motion
motion.dev		 React, and specifically: animating things that are being removed from the tree, layout animations, and springs. All three are painful by hand. ~18–34 KB
GSAP Choreography — a timeline with a dozen things at labelled offsets — and ScrollTrigger. Marketing pages, hero sequences, scroll-driven narrative. ~23 KB + plugins

The first three are free in every sense: no download, no dependency, no version to keep current, and no risk that the animation is missing while a bundle loads. That is a real argument, not a purist one. Reach past them when there's a capability you actually need — not by default.

What the two libraries actually give you

Both get described as "animation libraries," which hides the fact that they solve completely different problems.

Motion solves React's problem, not animation's

Lesson 0005 named the hardest part of an exit: the element has to outlive the state change that removed it. In plain CSS you now know two answers — allow-discrete with @starting-style, or a setTimeout matching the duration. In React neither works, because when state says the component is gone, React removes it from the DOM on the next render and there is nothing left to animate.

AnimatePresence is the fix, and it is worth understanding that it is not magic: it keeps the component mounted after you've said to remove it, runs the exit, and then unmounts. Delayed removal, with the bookkeeping done for you.

Two more things Motion does that are genuinely hard by hand:

  • Layout animations. An element's position changes because the layout changed — an item was filtered out, a card moved to a new column. Motion measures before and after and animates the difference with a transform. That's the FLIP technique, and doing it by hand is measurably annoying.
  • Springs. Motion expresses stiffness and damping instead of duration and curve, which is a different model of time — one that survives interruption naturally because the spring just gets a new target. That's its own lesson.

No JSX in this lesson, deliberately. When Motion arrives properly it gets a lesson of its own, with the React parts introduced slowly.

GSAP solves choreography

Everything in lesson 0003 was one group with one stagger, which CSS handles fine. GSAP earns its place when the sequence has structure: this starts, then this overlaps by 0.2s, then these four stagger, then the whole block reverses on a scroll-out. A GSAP timeline is a first-class object — you can name positions, insert relative to a label, reverse the whole thing, and seek to any point in it.

Expressing that in CSS means hand-computing every delay, and then re-computing all of them when you change one duration. That arithmetic is the plumbing GSAP saves you.

The other half is ScrollTrigger, which is the scrub half of lesson 0004 done properly — pinning, snapping, scrub with smoothing, and a set of callbacks at the boundaries. Native scroll-driven CSS is genuinely closing the gap for simple cases; it does not yet do pinning.

Worth knowing

Your north star, claude.com/claude-for-chrome, is GSAP. Emil Kowalski's work, the other north star, is mostly CSS and Motion. Both are correct choices for what they are: a choreographed marketing page, and interactive product UI. The tool follows the job.

The decision, in the order you should ask it

Five questions, top to bottom
  1. Can it be two states? → CSS transition. Stop here most of the time.
  2. Does it loop, or have 3+ steps, or run unprompted? → CSS keyframes.
  3. Do I need to pause, seek, reverse from here, or await the end? → el.animate().
  4. Is it React, and is the thing unmounting — or moving because layout changed? → Motion.
  5. Is it a sequence with structure, or scroll choreography with pinning? → GSAP.

Read that top-down and take the first yes. The order isn't arbitrary — it goes from least to most machinery, and the honest observation about production code is that most of it should stop at line 1 and a lot of it stops at line 2.

The mistake this lesson exists to prevent

Reaching for GSAP to fade in a card.

It's a common one, and it doesn't look like a mistake, because the result is fine. The cost is indirect: a dependency for something the platform does natively, an animation that can't start until JavaScript has loaded and parsed, and — the part that actually bites — the loss of the free interruptibility you got in lane 1 of the lab. GSAP can be interruptible, but you have to arrange it.

The inverse mistake is rarer but more expensive: hand-writing a twelve-step timeline with setTimeout because adding a library felt like defeat. If you find yourself maintaining a table of delays, the library was always the right call.

What doesn't change, no matter what you pick

Everything that matters, which is the actual point of this lesson.

  • Ease-out for entrances, ease-in for exits. GSAP calls it power2.out; Motion takes an array or a named ease; CSS takes a cubic-bezier. Same curve.
  • Exits run about half the entrance. No library defaults to this. You have to decide it.
  • transform and opacity are free; everything else buys pipeline stages. GSAP animating width costs Layout every frame exactly like CSS animating width does.
  • Overlap ≤ 0.35, and check the total separately. GSAP's stagger makes the arithmetic easier; it does not make a 2-second hero entrance acceptable.
  • prefers-reduced-motion is yours to honour in all five.

A library that made those decisions for you would be a design system, not an animation library. None of these are.

A dropdown opens and closes. The user can click the trigger rapidly. What should it be built with?

Two states, and interruption matters — which is exactly the transition's one superpower. It interpolates from the current computed value, so a half-open menu closes from half-open. A keyframe animation would snap; GSAP would work but you'd be arranging by hand what you get for free.

You need to know the exact moment an animation finishes, so you can focus an input afterwards. Cheapest tool?

WAAPI is built into the browser and gives you a real promise that resolves when the animation actually ends — no duplicated duration constant to drift out of sync. (A transitionend listener also works, but it fires per property and can be missed if the transition is interrupted.)

A list re-orders when the user changes the sort. Items should slide to their new positions. This is React.

Positions change because layout changed, so you can't know the distances ahead of time — they have to be measured before and after and played back as transforms. That's FLIP, and it's precisely what Motion's layout animations do for you. Transitioning top would also cost Layout on every frame.

A single card fades and slides up when the page loads. Which tool?

No interruption, no seeking, no sequence. Every tool produces an identical result, so the cheapest one wins — and the CSS version starts painting without waiting for a script. This is the case the lab's Play button was making.

Which of these does choosing GSAP actually decide for you?

This is the whole lesson. Tools differ in what they let you express and control. Duration, curve, purpose and restraint are yours in every one of them.
