Lesson 0014 · 18 minutes

Reading a Performance recording

A flame chart is not a grade. It is a trail of evidence: find the long frame, follow the work, then choose the smallest honest fix.

Skill: diagnose a slow animation from the work it causes← Lesson 0013

Lesson 0013 gave clip-path a careful warning: it skips layout, but it still buys paint. Today we look at the receipt. A performance recording is a timeline of frames and the browser work inside each one.

Say it out loud

Frame budget is the time available for one frame — about 16.7ms at 60Hz. A long frame misses that window; repeated misses feel like jank, a hitch in motion. Layout measures geometry, paint fills pixels, and composite assembles already-painted layers.

Start with this deliberately small recording. It uses the same question you will ask in DevTools: what changed, how much changed, and which pipeline stage paid for it.

Try this, in order
  1. Press Play recording, then Inspect worst frame. Read the verdict, not just the number.
  2. Change What changed from transform to clip-path to width. The stage named in the verdict follows the property.
  3. Leave the property alone and switch to 100 images. Scope matters: the same mechanism can cross the budget when more pixels are involved.
  4. Click a bar. A real recording lets you do the same thing: select one frame, then read the work nested inside it.

Three moves through a recording

1. Scan the frame track. Long bars are the places to investigate. Do not average them into an FPS score; one 42ms frame is a visible hitch even if the next ten are short.

2. Follow the pipeline. In the selected frame, look for Style, Layout, Paint and Composite. If Layout appears on every tick, geometry is changing. If Paint dominates, the browser is redrawing pixels. If only Composite remains, the main-thread work is probably not your bottleneck.

3. Name the mechanism before the remedy. “Make it faster” is not a diagnosis. Replace a moving width with a transform when the design allows it; reduce painted area when a reveal is too expensive; remove work that the interaction does not need. Keep the visual promise intact.

Before you press Record

A recording is an experiment, so set up the experiment before interpreting its result. Use the same viewport and zoom you use when judging the design. Close a noisy tab, but do not chase a laboratory-perfect machine: the page still has to feel good on an ordinary one. Turn on the Performance panel's Screenshots lane so you can line the trace up with what was actually visible.

Then decide what gesture you are measuring. A scroll reveal needs the scroll itself, not just the page load. A press state needs the press and release. Start recording, wait a beat, perform the gesture at a normal speed, and stop immediately after the last visible change. The quiet seconds before and after are useful boundaries; they show you which work belongs to the interaction.

Make a prediction first

Write one sentence before you record: “I expect this reveal to spend most of its time in Paint, because the visible window changes.” If the trace disagrees, that is good news — you have learned something about the implementation instead of confirming a hunch.

What the coloured rows mean

The top overview is a map, not the territory. The frames row tells you when the browser missed its deadline. The main-thread flame chart tells you what occupied that frame. A wide purple block is Layout; a green block is Paint; scripting is usually yellow. The colours are useful shorthand, but the width is the evidence: a five-millisecond Paint event is not a problem merely because it is green.

Look for relationships between rows. A click or scroll marker is your cause. A run of long frames immediately after it is the effect. If a long yellow task sits before the rendering work, JavaScript may be starving the frame. If the yellow work is short but Paint is wide, changing the script will not cure the bill. Select the largest child event, then move one level up and ask which interaction owns it.

Do not mistake a single requestAnimationFrame callback for the animation itself. It is a scheduling hook. The expensive part is the style, layout or paint work it causes afterward. Likewise, a green “composite layers” row is not proof that the whole page is cheap — image decoding, scripting and layer creation can happen elsewhere in the same frame.

Prove the fix

Change one mechanism at a time and record the same gesture again. Keep the viewport, scroll distance and speed as close as you can. Compare the worst frame and the shape of the run, not just the average. A successful transform substitution should remove Layout from the selected frames; it does not need to produce a magical “60 FPS” badge.

  1. Save the first recording or a screenshot of the selected frame.
  2. State the smallest change that could remove the dominant stage.
  3. Make that change, reload, and repeat the gesture three times.
  4. Check that the visual promise still holds — the reveal must still uncover, the drag must still track the hand, the press must still acknowledge the click.

If the number improves but the design feels worse, the optimisation failed. Performance is a constraint on the promise, not permission to quietly change the promise.

Go and look at a real page

Open the Image Reveal CSS demo. It is a good specimen because the visual idea is clear: an image is uncovered as you scroll, using a view timeline and clip-path.

  1. Open DevTools → Performance. Start a recording, scroll slowly through two or three reveals, then stop.
  2. Find one long frame in the overview. Select it and expand the main-thread events until you can name the largest stage.
  3. Record the observation in one sentence: “The reveal spends most of this frame in ___ because ___.” Repeat once with a cold reload and once with the cache warm.

This is not a benchmark. Your machine, browser, viewport and image cache all change the numbers. The transferable skill is reading the causal shape of the trace.

When the recording disagrees with the design

A short recording can lie by omission. Repeat the interaction, include the slowest part of the gesture, and check that the element is actually visible. A reduced-motion preference may remove the animation while leaving the layout and paint work you are trying to understand. The useful question is always: what work happened in the frame I can feel?

You can now

Find a long frame, identify the pipeline stage inside it, and propose a fix that follows from the mechanism rather than from a superstition about FPS.

What is the first useful target in a recording?

Long frames are the moments a person can feel; inspect those before summarising.

Which change usually skips Layout?

Transforms move a composited layer without changing geometry.

What should a verdict name?

A number is useful only when it is tied to the work that produced it.
