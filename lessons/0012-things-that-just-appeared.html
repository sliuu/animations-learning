Lesson 0012 · 18 minutes

Things that just appeared

A transition needs two values and a new element only has one. Everything in this lesson is a different place to put the missing one — and the choice between them is not cosmetic.

Skill: animate an element that has no previous state, and pick the mechanism from whether it can be interrupted ← Lesson 0011

Lesson 0011 was about an element that was already on screen and is now somewhere else. This is the case before that: an element that was not on screen at all, and now is. It looks like the easiest animation in the course. It is the one that most often does nothing at all, quietly.

A CSS transition interpolates between two computed values. Two. Append a row to a list and its very first computed style — opacity: 1, no transform — is also its final style. There is no pair. Nothing goes wrong, so nothing is reported: the transition was simply never eligible to start.

Which means every entrance you have ever written had to manufacture that first value. There are three places to put it, they are not interchangeable, and choosing badly costs you something you will not notice until a user changes their mind. The lab runs the same 380ms and the same eight pixels through all three — plus the version with none at all, which is the one to press first.

Try this, in order
  1. Leave the mechanism on transition only and press Add a row. Then read the line under the stage.
  2. Switch to @starting-style — that clears the list — and press Add all four for me.
  3. keyframe animation, same button. Watch the count change from transitions to animation.
  4. force a frame (JS), then open The code behind it and put it next to the second one.

Nothing ran

The first mode is not a broken demo and it is not a straw man. It is the code everybody writes first, and it is entirely reasonable-looking: there is a transition declaration on the row, the values it names are the values that change, and the row appears. The count under the stage is the only thing that will ever tell you.

getAnimations() is the instrument to remember. It returns every transition and animation currently attached to an element. When an entrance does nothing and you cannot see why, it answers the only question that matters — did the browser create anything at all? — and it distinguishes the two failures that look identical: nothing started (zero) from something started and it is wrong (one, going the wrong way).

Three places to put the first value

MechanismWhere the "before" livesReach for it when
transition alone nowhere never — this row is the bug, not an option
@starting-style a rule that only applies during the element's first style update, and is unreachable afterwards the entrance can be interrupted, or it shares properties with an exit
@keyframes … from inside the animation's own timeline fire and forget: it arrives, it stays, nobody can cancel it
start class + forced reflow a class your script adds and removes a frame later the start value is a number you had to measure

@starting-style is worth one sentence of precision because the name suggests something more magical than it is: it is an ordinary rule that is only ever consulted once, on the style update where the element first has a style — when it enters the document, or when it comes out of display: none. After that it may as well not exist. That is why the rows already sitting in the list in step 2 did not move: they had their first style update several presses ago.

Where you put the zero

Look at where opacity: 0 actually lives in each of those. In @starting-style it lives in a rule that becomes unreachable. In a from keyframe it lives inside the animation. In neither case is it the element's resting state.

Compare the pattern you will meet most often in real code:

.row      { opacity: 0; transform: translateY(8px); transition: … }
.row.in   { opacity: 1; transform: none; }

Here the zero is the resting state, and the element is only visible because something added a class. Lesson 0004 called that the cardinal sin of scroll reveals and gave you the fix — hide nothing unless a .js class proves a script ran. That fix is still correct and you should still use it. What is worth noticing now is that the other two mechanisms do not need it: with @starting-style or a from keyframe, an element that never animates for any reason is a visible element that did not animate. The failure mode is boring, which is the highest praise an entrance can get.

Principle

Put the start value somewhere that only exists during the entrance. A start value that lives in the resting rule has made your content conditional on your animation running.

The gate: can she change her mind?

Two of those mechanisms will animate a new row and you cannot tell them apart by looking. 0011 ended on the question that separates them, in a different costume: can the user interrupt this? There it decided between FLIP and a view transition. Here it decides between a transition and a keyframe animation, and it is the same question with the same teeth.

Both panels below are the same notification, opening with the same 420ms and the same curve, closing with the same 320ms. One press drives both, because the difference is a thing you feel and a feeling does not survive being remembered.

Why A jumped

A transition has no timeline. It holds a start value, an end value and a curve, and when the end value changes it recomputes the start from what is on screen right now. That is why B's exit began at 0.76: 0.76 was the truth at that moment, and a transition has no other source of truth.

A keyframe animation does have a timeline, and swapping one animation for another starts the new one at its own zero. @keyframes out opens with from { opacity: 1 } and it means it — regardless of whether the entrance had got there. So the panel snaps to fully arrived and then leaves, which reads to a user as the interface briefly ignoring them.

Notice what panel A is not doing wrong. Its keyframes are correct, its curves are the ones this course would pick, and the JS that keeps it mounted for the length of its exit is the same bookkeeping lesson 0005 showed you and the same job AnimatePresence does in Motion. It is careful code. It simply cannot know where the entrance had got to, because a from keyframe is an assertion, not a question.

And at 500ms nothing disagrees, because by then there was no entrance left to interrupt. The whole difference exists only during flight. If you test an entrance by opening it, waiting, and closing it, you will never see this — which is exactly why it ships.

You can have both, by leaving CSS. el.animate() hands back an Animation object with reverse() and a settable playbackRate, so a JS-driven animation can be turned around properly. You just have to hold on to the object and decide to.

0006's ladder, again: the transition gives you interruptibility as a property of the mechanism, and the Web Animations API gives it to you as an API you must remember to call.

The gate

Can the user cancel this before it finishes? No — a keyframe animation, and stop thinking about it. Yes — @starting-style and two rules, because the entrance has to be able to become an exit.

Rows in a feed, a toast that has already committed, a hero on load: no. Anything with a close button, a backdrop, an Esc key or a finger on it: yes.

When the "before" is a number you had to measure

The fourth mode of the first lab is the one that looks the most primitive and is the most general. Its start value lives in a class the script adds before insertion and removes a moment later, and between those two moments there is one line doing all the work:

void row.offsetWidth;

Which is 0011's line, in the other direction. There it made an inverted position real enough to transition away from; here it makes a start position real enough to transition away from. Same problem both times: the browser batches style changes within a turn of the event loop and collapses any value that would never be painted, and a forced layout read is how you insist that one of them was real.

Worth remembering as one sentence

@starting-style is a declarative void el.offsetWidth. Both exist to make one particular style real enough that the browser will transition out of it.

So why keep the primitive one? Because a stylesheet can only hold values you can type. FLIP's before is translate(-329px, -66px), computed at runtime from two measurements, and there is no rule you could have written for it. When the start value is data, it has to be set from script, and then it has to be flushed. That is the whole of the fourth row of the table.

Popovers, dialogs, and the one that still catches people

Everything above applies unchanged to <dialog> and the popover API, with one extra term. These elements are promoted to the browser's top layer — a layer above everything on the page, which is how a modal escapes an ancestor's overflow: hidden without anyone managing z-indexes. Promotion and demotion are controlled by the browser, not by your CSS, and demotion is instant by default.

Which produces a specific and confusing bug: the popover fades out correctly, and vanishes anyway on the first frame, because it left the top layer while it was still mid-fade. Four declarations fix it and three of them are already familiar:

[popover] {
  opacity: 0;
  transition:
    opacity 200ms cubic-bezier(0.4, 0, 1, 1),
    display 200ms allow-discrete,   /* keep it in the box model … */
    overlay 200ms allow-discrete;   /* … and in the top layer */
}
[popover]:popover-open { opacity: 1; }

@starting-style {
  [popover]:popover-open { opacity: 0; }
}

The pairing is the thing to hold on to: display keeps the element rendered, overlay keeps it on top, and forgetting the second gives you an exit that is technically running and visually absent. overlay can only be transitioned this way — it is not a property you are allowed to set yourself, only one you are allowed to delay.

Where it runs

@starting-style and transition-behavior: allow-discrete shipped together and are in all three engines: Chrome 117, Safari 17.4–17.5, Firefox 129. The popover API is a little older and a little wider. Transitioning overlay is Chromium only at the time of writing, which is survivable — without it the exit is a hard cut in those browsers, and a hard cut is the un-animated baseline rather than a broken page.

Check MDN's compatibility tables rather than trusting numbers written in a lesson; the point of quoting them is the shape of the degradation, not the versions. In every case here it is the same shape: the element still appears, still disappears, and still works. That is what makes these safe to reach for without a feature query — unlike 0004's scroll-driven animations, where the un-animated fallback would have been an invisible page and the @supports gate was load-bearing.

A row is appended to a list. It has a transition on opacity and transform, and it appears instantly with no fade. What does the console show?

A transition needs two computed values and the row only ever had one, so no transition was created. getAnimations() returns 0, and that is the instrument for this class of bug — it separates nothing started from something started and it is wrong.

A drawer opens over 400ms. The user can close it with a backdrop click at any point. Which mechanism?

The gate is interruptibility. A backdrop click at 120ms is a mid-flight reversal, and only a transition recomputes its start from what is on screen. Swapping to an exit animation restarts the timeline at from, so the drawer snaps to fully open and then closes. fill-mode governs what happens outside the animation's active period, not where a different animation begins.

Why can't @starting-style replace the start class and forced reflow in a FLIP animation?

The invert is a number like translate(-329px, -66px) that depends on the viewport, the content and where the shuffle landed. There is no rule you could have written. Option two is also true and is a second, independent reason — but the general one is that a start value which is data has to come from script.

A popover fades out over 200ms with display … allow-discrete in its transition. It still disappears instantly. What is missing?

display keeps the element rendered; overlay keeps it on top. Top-layer membership is the browser's to grant and revoke, and the only control you have over it is permission to delay the revocation. @starting-style is consulted on the way in only, and none of this needs a JS listener.

What you can now do

Write an entrance for something that did not exist a moment ago, and say which of three places you put its start value in and why. When an entrance silently does nothing, reach for getAnimations() before reaching for the prose. And when someone asks whether an entrance should be a transition or an animation, answer with a question about the user rather than about the syntax: can they change their mind while it is running?
