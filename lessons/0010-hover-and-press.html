Lesson 0010 · 20 minutes

Hover and press

The first lesson where the timing is set by the hand on the other end rather than by the element on the screen — and where half of what you write doesn't exist on a phone.

Skill: time a state change to the hand that caused it, and gate it on the input device ← Lesson 0009

Every animation in this course so far has been the page acting. Hover and press are the page answering.

That changes two things. First, the clock started before your animation did. Nobody has an expectation about when a scroll reveal should fire — but a finger that has already moved is waiting for the screen to agree, and it is counting. Second, whether half of this code runs at all is decided by hardware you don't control. There is no hover on a phone. Not "hover is awkward on a phone" — the event that turns a hover state off is never generated at all.

Try this, in order
  1. It starts in mouse. Hover the button, then press and hold it, then drag off it while still holding.
  2. Press Tap it for me. That switches to touch and performs exactly one tap. Don't touch anything after it finishes — just watch the panel.
  3. Read the event log and name the event that never arrives.
  4. Switch how the hover rule is written to gated and tap again.
  5. Back to mouse. Drag press-down duration to 400ms and press the button.

What you just saw

On the mouse, a hover state is self-cancelling. pointerenter turns it on, pointerleave turns it off, and you never think about it again. That symmetry is the only reason bare :hover has ever worked.

A finger doesn't do that. It arrives out of nowhere and it leaves without a forwarding address, so browsers on touch devices synthesise the mouse half: on tap they apply :hover, and — having no leave event to work with — they keep it applied until you touch something else. Your button stays lit. Your card stays raised. The dropdown you were proud of stays open behind the page the user has already moved on to.

This is not a browser bug. It's a browser doing the only reasonable thing with a rule you wrote for a device that isn't there. The fix is to stop writing that rule for that device:

@media (hover: hover) {
  .btn:hover { background: var(--accent-700); }
}

Note what is not inside those braces. :active stays outside. A finger cannot hover, but it can absolutely press — that's the entire input.

The mistake this lesson exists to prevent

Putting :active inside @media (hover: hover). It happens by copy-paste: you have a block of interaction styles, you wrap the block, and the press feedback goes with it. Touch users — the majority on most consumer sites — now get a button that does nothing at all when they push it. It looks fine on your laptop forever.

The 0.1 second line

Press-down has a hard ceiling, and it isn't taste. But a number you're told is a number you forget, so find it yourself first. The two buttons below are identical except for one value, and which side holds which is shuffled — so your first press is an opinion, not a confirmation.

Try this, in order
  1. Press A. Press B. Press A again. Use your own hand — this is the one demo in the course that can't be watched, only felt.
  2. Decide which one you'd ship. Then press Which is which?
  3. Drag the one slider back towards the other side and find the point where you can no longer tell them apart. Write that number down before you read on.
  4. Switch to release. Same drill — press both, commit, reveal.
  5. Switch to who moved first and press each side several times.

The number you found in step 3 was probably somewhere near a tenth of a second. It isn't a coincidence and it isn't about buttons. Jakob Nielsen's three response-time limits named it in 1993:

0.1 second: Limit for users feeling that they are directly manipulating objects in the UI.

Past that line the feeling changes category. Under it, you pushed the button. Over it, you asked the computer to push the button and it did, shortly afterwards. Nothing about the pixels changed — the same 4%, the same curve — but the sense of touching the thing is gone. That is why the lab hides which side is which: told in advance that 400ms is worse, you would have agreed without ever checking, and this is a limit you want in your hands, not in a note.

So: press-down 0–100ms. Zero is a legitimate answer. And a useful corollary — at 80ms, every easing curve in Reference 01 looks identical, because there aren't enough frames to tell them apart. This is the one place in the course where you can stop thinking about the curve. Use ease-out and spend the attention elsewhere.

Down fast, up slow

That's the release tab. One side uses a single duration for both directions, which is what almost everyone ships; the other goes down fast and comes back slowly. Every setting of the symmetric side fails, and they fail differently — fast-and-symmetric snaps back like a switch, slow-and-symmetric breaks the ceiling you just found. No single number works in both directions, which is the whole point:

.btn {
  transition: transform 180ms var(--ease-out);   /* coming back up */
}

.btn:active {
  transform: scale(0.96);
  transition: transform 80ms var(--ease-out);    /* going down */
}

Note that the release duration is declared on the base rule and the press duration inside :active. A transition belongs to the state being entered, so the rule that turns the press on owns the going-down time, and the resting rule owns the coming-back time. Override only the transform and you get one duration in both directions by accident — which is exactly B.

Going down is your action, so it has to be instant. Coming back up is the system letting go, and a slightly soft release reads as physical resilience — you get most of what a spring would give you for one extra line and no library.

Who moved first

Now the third tab, which is the one that matters beyond this lesson. Both sides spend the same number of milliseconds. One spends it on a panel it slides in for you; the other spends it on the button under your finger. Push the slider to 300ms and press each a few times.

300ms on the panel is unremarkable — it's Reference 02's number for exactly that kind of move. 300ms under your finger is broken. Same duration, same curve, same property, opposite verdict. So the duration was never a property of the animation; it was a property of who started it.

The rule this gives you

Motion that answers the user is as close to instant as you can make it. Motion the system starts on its own gets a duration.

A press-down answers a finger, so it's 80ms. A dismissal is the system removing something on your behalf, so it's 180ms. It was never about "in versus out" — it's about who went first.

This is also why lesson 0005's rule — exits run about half the entrance — isn't a separate fact to memorise. An exit is usually the system clearing something away, an entrance is usually the system bringing it in, and both are on the system's side of the line. The moment a gesture crosses it, the halving rule stops applying and the tenth of a second takes over.

Why scaling down reads as "physical"

Of the free properties from lesson 0002, scale is the only one that maps onto a physical press. Smaller means further away; further away under a finger means pushed. Opacity has no direction, rotation has the wrong one, and translation reads as the button sliding rather than yielding — though a 1px translateY is a good second choice when you want a key rather than a surface.

The number is not a constant, though. Scale is a ratio and displacement is what the eye reads, so the same scale on a bigger element is a bigger move:

edge displacement = (1 − scale) × width ÷ 2

Keep the edge displacement in the 2–4px band and derive the scale from the width, rather than reusing 0.96 everywhere and wondering why it looks wrong on the big cards. For anything full-width, stop scaling and darken the background instead — no displacement, same acknowledgement.

Origin matters here too, and lesson 0007 already gave you the rule: scale from where the gesture is anchored. For a press that's the centre, because the finger is somewhere in the middle of the target and the whole surface is yielding together. It's the one common case where the default transform-origin is also the right answer — which is why it's easy to forget it was ever a decision.

:hover, :active, or JavaScript

Reach forWhenWatch for
:hover Any hover decoration. Always. It costs nothing and needs no state. Latches on touch. Gate it.
:active Press feedback, on every device. It also fires for a keyboard user pressing Enter or Space on a real <button>, which you get free. iOS Safari has historically not applied it on tap unless the element or an ancestor carries a touch listener — the folk fix is <body ontouchstart="">. Test it on a device; don't assume either way.
Pointer events When the press has to survive the pointer leaving the element (a drag handle, a slider, hold-to-delete), or when the state has to exist in JS anyway. setPointerCapture is the piece people miss — without it, a drag dies the moment the cursor exits the element's box.

The ladder from lesson 0006 applies unchanged: two pseudo-classes cover the overwhelming majority of hover and press work, and reaching for pointer events when :active would do is how a button acquires 40 lines of state management and a bug where it stays pressed.

Gating it properly

There are four media features here and people reach for the wrong two. hover and pointer describe the primary input; any-hover and any-pointer describe any input the device has.

QueryMeansUse it for
(hover: hover)The primary input can hover Hover decoration. This is the one you want.
(any-hover: hover)Some input can hover Rarely. It's true on a tablet with a trackpad attached — where the person is usually still using their finger.
(pointer: coarse)The primary input is imprecise Hit-target sizing, not motion. A different problem that happens to correlate.
(prefers-reduced-motion)Covered in 0009Composes with all of the above.

You will see @media (hover: hover) and (pointer: fine) a lot — Reference 01 says it, and I'm walking it back here. The and (pointer: fine) narrows the query to devices with a precise pointer as well, which excludes hover-capable inputs that aren't precise, and buys you nothing: sticky hover is caused by the absence of a leave event, not by imprecision. Gate on hover alone.

And note the direction of failure, which is the same argument 0009 made for Tailwind's motion-safe:. Writing the positive query — "when hovering is possible, add this" — means that forgetting the query leaves you with no hover effect, which is a nicety missing. Writing the negative one — "when hovering is impossible, undo this" — means forgetting leaves a stuck state on a phone. Prefer the version whose failure mode is boring.

The line you can't cross

Never put information or a control behind hover. The "…" menu that only appears on row hover, the tooltip that holds the only explanation of an icon, the delete button that fades in — on a phone these do not exist, and to a keyboard user they never appeared either. Hover may add emphasis to something already visible. It may not be the thing that reveals it.

Hover intent, in CSS

A cursor crossing your nav on its way to somewhere else shouldn't set off every submenu it passes over. The usual answer is a JavaScript timer; the usual answer is usually unnecessary. An asymmetric transition-delay does it:

.tip {
  opacity: 0;
  transition: opacity 120ms var(--ease-out);
  transition-delay: 0ms;        /* leaving: go now */
}

.trigger:hover .tip {
  opacity: 1;
  transition-delay: 300ms;      /* arriving: wait and see */
}

The delay applies on the way in and not on the way out, so a cursor passing through gets nowhere near 300ms and nothing happens, while a cursor that stops gets its tooltip. Leaving is immediate because the person has already decided.

JavaScript earns its place here in exactly one case: a submenu the cursor must cross a gap to reach, where it briefly leaves the trigger and hasn't arrived at the panel. That's the "safe triangle" problem, and it needs real cursor-trajectory logic. Everything short of it is a delay.

Keyboard gets neither

A keyboard user never hovers and never presses, and they are the reason this can't be left as a CSS detail. Any hover state that signals this is interactive needs a :focus-visible twin — not necessarily an identical one, but something in the same place doing the same job.

.btn:focus-visible { outline: 2px solid var(--ink); outline-offset: 2px; }

:focus-visible rather than :focus because the browser already knows the difference between a click and a Tab and will only show the ring for the one that needs it. This is why the old outline: none reflex is unnecessary as well as harmful — the problem it was solving no longer exists.

What reduced motion does to all of this

Good test of 0009's three buckets: where does press feedback go? Try to answer before reading on.

It's the safest thing on the page. Check it against the risk table: tiny area, no parallax, no depth manufactured beyond a 2px edge move, monotonic, short, and — the bottom row of that table — it answers a gesture the user just made. A press scale is at the safe end of every axis at once. Keep it under reduce.

What you do cut: hover effects with real travel. A card that rises 8px, a row that slides right, an arrow that shoots sideways. Same treatment as everything else — set the distance to zero and keep the colour change:

.card { --lift: 6px; }
.card:hover { transform: translateY(calc(var(--lift) * -1)); background: var(--paper-2); }

@media (prefers-reduced-motion: reduce) {
  :root { --lift: 0px; }        /* the same one-line switch from 0009 */
}

Three ways to get this wrong

  1. Press feedback slower than hover feedback. If the button responds faster to being looked at than to being pushed, the hierarchy is inverted and it reads as broken without anyone being able to say why. Press is always the fastest thing on the element.
  2. Hover states on things that aren't interactive. A card that lifts on hover is promising a click. If the whole card isn't clickable, you've spent the affordance on a lie and people will click the middle of it.
  3. Testing with a mouse only. Chrome DevTools' device toolbar changes the viewport and touch emulation, and the lab above simulates the event sequence — but neither is a phone. The sticky hover, the missing :active, the tap that fires twice: those show up on hardware. This is the same failure as shipping an unlooked-at reduced-motion version.

What this changes about the previous nine lessons

Lessons 0001–0009 all answered "how long should this take?" with a property of the thing: modals are 300ms, toasts are 180ms, heroes are 500ms. That was the right model because in every one of those cases the system went first.

From here on there's a second question in front of that one — who moved first? If the answer is the user, the duration budget collapses to a tenth of a second and the device they used decides which rules exist at all. Reference 02's duration table still holds; it just now has a row above it that overrules it.

Why does a hover state stay lit after a tap on a phone?

The browser synthesises the enter half of the mouse interaction on tap and has nothing to synthesise the leave half from. It's a symmetry your CSS assumed and the hardware doesn't provide.

Press-down 80ms, release 180ms. Why not the same number both ways?

Who moved first is the question underneath both rules. It also isn't 0005 inverted — 0005 is about the system removing something, which is a different actor from a finger pushing down.

A 320px-wide card uses scale(0.94) on press. What's wrong with it?

(1 − 0.94) × 320 ÷ 2 ≈ 9.6px. Scale is a ratio; displacement is what the eye reads. Derive the scale from the width to land in the 2–4px band — here about 0.985 — or darken the background instead.

Which of these belongs inside @media (hover: hover)?

A finger can press and a keyboard can focus; neither can hover. Wrapping the block is the most common real version of this bug, and it removes all press feedback for most of your users while looking perfect on your laptop.

Under prefers-reduced-motion: reduce, what happens to a 2px press scale?

It sits at the safe end of every axis in 0009's risk table at once. The third option is the 0.01ms reset in miniature — same displacement, minus the smoothing, which is the wrong half to delete.
