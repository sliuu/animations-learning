Lesson 0004 · 20 minutes

The scroll reveal, and the one that isn't one

Two completely different techniques share the name "scroll animation." Everything else in this lesson is downstream of telling them apart.

Skill: choose trigger or scrub, and place the fire point ← Lesson 0003

Everything you learned about a group entrance still applies. The only new variable is when it starts — and that one variable splits into two techniques that behave nothing alike.

In lesson 0003 the hero arrived on page load, and you chose the moment. Below the fold you don't: the reader chooses it, by scrolling, at a speed you can't predict. There are exactly two ways to connect scrolling to motion, they look identical in a screenshot, and picking the wrong one is the most common scroll-animation mistake on the web.

They're called trigger and scrub. Rather than define them at you, I want you to feel the difference first — it takes about a minute, and the rest of this lesson reads completely differently afterwards.

Try this, in order

1. The lab below opens in trigger mode. Press Scroll it for me and just watch the cards. You don't have to operate anything.

2. Press Stop halfway. Read the message that appears under the buttons.

3. Now click scrub at the top left, and do both again — Scroll it for me, then Stop halfway.

Step 3 is the whole lesson. The cards freeze part-way faded and stay there.

What you just saw

In trigger mode, scrolling past a point starts an ordinary animation — the same kind you've written in every lesson so far, with a duration and an easing curve. Once started it runs on its own clock and finishes no matter what the reader does next. Stop scrolling and it still completes.

In scrub mode, there is no clock. Scroll position is the animation's progress. Half-scrolled means half-animated, and it stays half-animated for as long as the reader sits there.

The word for this in animation tools is playhead — the marker showing which moment of an animation you're currently looking at, like the progress dot on a video. Normally time moves the playhead. In a scrub, the scrollbar moves it, and it goes backwards just as happily as forwards.

Now the comparison table is worth reading, because every row is something you just watched happen:

Who controls duration You. 400ms is 400ms. The reader's scroll distance and speed

Easing Yours, and it's felt Mostly meaningless — the reader is the curve

The rule this gives you

If the element carries meaning, trigger it. A headline, a paragraph, a statistic — anything someone has to read — must not have its legibility decided by where they happened to stop scrolling.

Scrub only what can be seen at any arbitrary percentage without loss: a background layer, a progress indicator, an image that drifts a little.

GSAP's ScrollTrigger does both, which is why people conflate them: scrub: true flips one into the other with a single property. In CSS the same split exists as animation-timeline: view() (scrub) versus an IntersectionObserver that adds a class (trigger).

Where it fires: the one number to get right

An IntersectionObserver fires when the element crosses the edge of a root box. By default that root is the viewport, and the edge is the very bottom — so the animation starts the instant one pixel of the element appears. That's too early: the element animates while it's still off-screen, and the reader arrives to find it already finished.

rootMargin moves that edge. It takes CSS-shorthand values and grows or shrinks the root box:

new IntersectionObserver(callback, {
  rootMargin: '0px 0px -15% 0px',   /* top right bottom left */
  threshold: 0
});

The sign rule, which everyone gets backwards once: a negative bottom margin shrinks the root box upward, so the element must travel further up the screen before it counts as intersecting — it fires later. A positive bottom margin grows the box past the viewport's edge and fires earlier, while the element is still below the fold.

Drag the fire point in the lab above and watch the dashed line move. Around -15% is a good default: the element is meaningfully on screen when it starts, and it finishes well before it reaches the reader's centre of attention. Push it to -45% and you get the classic bad version — the reader is already looking directly at the element when it decides to move.

threshold is the other knob, and it's the wrong one for reveals. It asks "what fraction of the element is visible," which for anything taller than the viewport can never be satisfied. Leave it at 0 and control the timing with rootMargin.

The cardinal sin, which you must never ship

Every scroll reveal works by starting the element at opacity: 0. Which means if the thing that's supposed to reveal it never runs, your content is invisible — not unanimated, gone. A JS error above your observer, a blocked script, a bot, a reader who scrolled past before the observer attached: all of these produce a blank page, and every one of them is a content bug, not an animation bug.

Never ship this

Hiding content in a stylesheet that only JavaScript can unhide. The rule is absolute: with the animation disabled, the content must still be there.

The fix is three lines and belongs in the <head>, before the browser paints:

<script>document.documentElement.classList.add('js');</script>

<style>
  /* Un-hidden by default. Only a page that ran JS gets to hide anything. */
  .js .reveal { opacity: 0; transform: translateY(20px); }
</style>

Same idea if you use CSS scroll-driven animations later in this lesson: the animated state is the exception, the visible state is the baseline. And it's why the reveal below the fold is always a fade in from hidden — never a fade out that you undo.

Stagger it by batch, not by index

Three cards in a row cross the line together, and you want lesson 0003's stagger. The tempting version is to key the delay off the element's index in the list. Don't — card twelve then waits twelve steps for something that started when card ten crossed. Stagger by position within the entries the observer just handed you:

const io = new IntersectionObserver((entries) => {
  let batch = 0;
  for (const entry of entries) {
    if (!entry.isIntersecting) continue;
    entry.target.style.transitionDelay = `${batch * 60}ms`;
    entry.target.classList.add('is-revealed');
    batch += 1;
    io.unobserve(entry.target);   // reveal once, then stop watching
  }
}, { rootMargin: '0px 0px -15% 0px' });

Two details worth naming. The observer batches entries that crossed in the same frame into one callback, which is exactly the group you want to treat as one gesture. And unobserve is not an optimisation — it's the thing that makes the reveal permanent.

Which is the other setting in the lab. Flip re-trigger to "every time" and scroll up and down: the content re-hides. The second viewing answers no question the first didn't, and on a page that people scroll back through it degrades into flicker. Reveal once.

The CSS version, with no JavaScript at all

Modern CSS can drive an animation from scroll position directly. animation-timeline: view() replaces the animation's clock with the element's own progress through the scrollport — which, by the table above, makes it a scrub. animation-range says which slice of that progress the animation occupies.

The range keywords are the part worth memorising: entry is the phase where the element is crossing into view, cover is the whole time any part of it is visible, and exit is it leaving. So entry 10% cover 30% means "start once 10% into entering, finish 30% of the way through the visible span."

Note three things in that CSS. The animation is declared inside @supports, so a browser without the feature simply shows the cards — the cardinal-sin rule, satisfied without any JavaScript. The timing function is linear, because the reader supplies the curve. And there's no duration, because animation-range replaced it.

Support is real but not universal, and it's moving; check MDN's compatibility table on animation-timeline rather than trusting a number written in a lesson. The @supports gate means you never have to care very much.

So which do you reach for? The honest answer for reveals is still the observer, because a reveal wants a trigger and CSS scroll timelines are a scrub. But scroll-driven CSS is genuinely better than JS for everything that should be a scrub — reading-progress bars, parallax, image reveals — because it runs off the main thread, and that's exactly lesson 0002's argument arriving in a new place.

Now the harder question: should it animate at all?

You can build these now, which makes this the right moment to ask — and the answer is often no. Scroll reveals are the single most over-applied effect on the web, and the argument against them is unusually strong. On page load, motion earns its keep by directing attention: the reader has just arrived and doesn't know where to look. Below the fold, they scrolled toward this section deliberately. They already committed. Their attention is not in question.

First principle

A scroll reveal cannot direct attention that has already been directed. So its only legitimate jobs are the remaining two: establish hierarchy within the section (this heading, then this data, then this caveat) and signal that a boundary was crossed (a new idea starts here).

If a section does neither — a wall of paragraphs, a footer, a nav — the correct amount of scroll animation is none. "Everything fades up 20px" is not a decision, it's a default.

Which is also the practical answer to the most common failure mode: revealing so much, so often, that a reader scrolling at normal speed is permanently reading content that is still in motion. Reveal sections, not paragraphs.

Reduced motion

The full treatment gets its own lesson. The scroll-specific version is short: remove the travel, keep the fade. A reader who asked for reduced motion still needs to see the content appear, and a 200ms opacity change is not what they were objecting to.

@media (prefers-reduced-motion: reduce) {
  .js .reveal { transform: none; }
  .is-revealed { transition-duration: 200ms; }
}

Deleting the reveal entirely is also fine — as long as the un-revealed state is visible, which it is, because you followed the rule at the top.

A testimonial section fades up on scroll. QA reports it's blank for one user. What's the most likely cause?

The starting state is opacity: 0. If a script error, a blocker or a bot prevents the reveal from running, the content is gone rather than just static. Gate the hidden state behind a class JS adds to <html> before paint.

You want a section heading to start animating later — further up the screen. Which change does that?

A negative bottom margin shrinks the root box upward, so the element has to travel further before it intersects — it fires later. Positive grows the box past the viewport and fires earlier. Threshold asks a different question entirely, and can't be satisfied by an element taller than the viewport.

A pull-quote is bound to scroll with animation-timeline: view(). A reader stops mid-scroll. What have you shipped?

Scroll position is the playhead, so progress freezes wherever the reader stopped. That's correct behaviour for a progress bar and wrong for anything carrying meaning. Text wants a trigger.

Twelve cards use transition-delay: calc(var(--i) * 60ms) with --i as the DOM index, revealed by an observer. What breaks?

The 0003 pattern assumes all twelve start at the same moment, which is true on load and false on scroll. Card twelve crosses the line in its own batch and then waits 660ms for nothing. Stagger by index within the observer's batch.

Which of these is the strongest case for scroll animation at all?

As the section above argues: attention is already committed by the time someone scrolls, so the only remaining jobs are hierarchy and boundary. Three numbers in priority order is hierarchy. Body paragraphs animate content the reader is actively trying to read; a footer has no hierarchy to express.
