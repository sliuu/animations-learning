Lesson 0013 · 17 minutes

Reveals with clip-path

Wipes and masks: the difference between the thing moving and the window over it moving, and how to tell when a rectangle would have done the job for free.

Skill: reveal something without moving it, and know before you write it whether the shape is worth a paint ← Lesson 0012

Lesson 0012 was about an element that had no previous state, and all three answers did the same thing: manufacture the missing first value on the element. A starting opacity, a starting transform, a first keyframe. This lesson is about the other place a change can live — not on the element at all, but on the window in front of it.

Both get called a reveal. In one, the thing moves and fades into position. In the other, the thing was there the whole time, fully painted, at rest, and the only thing that changes is how much of it you are allowed to see.

One press drives both panes below, at the same duration and the same easing. The right-hand pane is the fade-and-rise this course has recommended since 0001, built properly — it is not the bad option, it is the other one. Watch the headline rather than the card.

Try this, in order
  1. Press Reveal both on wipe from the left, then read the two badges under the panes.
  2. Drag duration up to about 900ms and press again. Slow enough to see, and the badges say the same thing.
  3. Switch to open from the centre line, then iris out. Look at the right pane's label while you do.
  4. Tick move the content inside the window too and press again — that is the combination most reveals in the wild actually are.

Two effects, one word

The left pane never renders the headline at partial opacity and never moves it. At any frame you could stop on, the type is either absent or finished — full weight, full contrast, in its final position. The right pane spends its whole flight rendering type that is dimmer and lower than the type you are meant to read.

Neither of those is wrong, but they say different things. A masked reveal reads as uncovering something that already exists: an editorial header, a hero line, a value that was computed before you asked. A fade-and-rise reads as arriving: a new row, a toast, a result that did not exist a moment ago. When a designer says a reveal feels "too soft" or "too tentative", nine times out of ten they are describing a fade where a mask was wanted, and the fix is not a different easing curve.

The three shapes where the right pane's label changes to opacity only — no equivalent are the real argument. There is no way to move a block of type so that it arrives from its own centre line, or from a hole in the middle of itself. Those pictures exist only if something is clipping.

The shape is what stays

clip-path takes a shape and keeps what is inside it. Everything outside is not drawn — not transparent, not moved, not there. The element's layout box does not change, so nothing around it reflows, and hit-testing follows the visible shape.

clip-path: inset(0 100% 0 0);      /* right edge all the way in */
clip-path: inset(0 0 0 0);         /* every edge at rest: all of it */
clip-path: inset(0 0 0 0 round 14px);   /* the card's own corners */
clip-path: circle(0% at 50% 52%);  /* a radius, and its centre */
/* any straight-edged shape, and percentages may go outside 0-100% */
clip-path: polygon(0 0, 134% 0, 100% 100%, -34% 100%);

The four numbers in inset() are distances inward from top, right, bottom and left — the same order as margin. So a left-to-right wipe is one number moving from 100% to 0, and the direction of the wipe is which edge you chose to animate. Percentages in a polygon may go outside 0–100%, which is how the diagonal gets its overhang: the top-right corner sits at 134% so the tilted edge finishes past the card instead of cutting the corner off.

There is one rule that will cost you an afternoon if you learn it the hard way. A shape only interpolates against its own kind. Inset to inset, circle to circle, polygon to polygon with the same number of vertices. Cross a type boundary — inset to circle, or a four-point polygon to a five-point one — and there is no animation: the browser holds the first shape, swaps to the second at the halfway mark, and holds that. It is not an error and nothing is logged, so it looks exactly like a broken duration.

Same failure mode as 0012's, in a different costume: the animation was never eligible, so there is nothing to report. The instrument is the same too — getAnimations() will show you a running animation with a sensible duration, which tells you the problem is the values, not the mechanism.

Practical consequence: if you need a rectangle to become a circle, build the rectangle as a circle() big enough to cover it, or as a polygon with the vertex count you will end on. Decide the shape family before you decide the animation.

What it costs, and the question that actually decides it

Lesson 0002 put clip-path in the on credit row: it skips layout, so it will never cause the catastrophic kind of jank, but it is not free the way transform and opacity are — it re-paints, and the bill scales with the area being painted rather than with how complicated the shape is.

That framing is true and it is also not how you make the decision, because "is it expensive" has no answer without a number of elements and a size. The question that decides it is a capability question, and you can answer it before you write anything: could a rectangle have done this? Below are three builds of the same reveal — one clipping with clip-path, two clipping with an overflow: hidden wrapper — and five things the reveal might be asked to do.

Try this, in order
  1. On just reveal it, press Reveal all three. Three identical pictures. Read what the left pane's verdict says about itself anyway.
  2. The type must not move — watch the third pane, and read the pixel count under each one.
  3. The window keeps the card's corners. This is the one that surprises people: the middle build fails and the cheapest build wins.
  4. A diagonal leading edge and open from the centre line. Both wrapper builds simply cannot, and they fail visibly rather than quietly.
  5. Then press Measure the cost at 48, at 120, and at 300 copies, and read the note under the table. That is your machine, not a blog post's.

The test, in four questions

Ask these in order, and stop at the first yes — a yes means the rectangle cannot do it and the paint is bought honestly.

  1. Is the leading edge anything other than horizontal or vertical? Diagonals, curves, irises, anything you would describe as a shape. overflow: hidden clips to a box and there is no declaration that tilts it.
  2. Does the window need more than one moving edge? Opening from a centre line is two edges at once. A wrapper is one window with one leading edge; two of them means two wrappers and two counter-transforms, which is more CSS than the shape was.
  3. Must the content stay perfectly still and keep a radius that stays put? Either one alone is available to a wrapper. Both together are not: the build that holds the type still is the one whose window travels, and a radius on a travelling window travels with it.
  4. Is the element you would have to wrap one you do not control? A wrapper is a new box in the layout — inside a grid, a flex row, or a component whose children someone else owns, adding one is a change to the layout, not just to the animation.

All four no? Then you are looking at a rectangle sliding behind another rectangle, and the two composited transforms are the answer — not because the paint would have been ruinous, but because you would be spending it for a picture you could have had for nothing. That is also the honest answer to the question 0002 left open, is animating clip-path actually safe: yes, at the scale a hero or a header runs at, and the measurement strip above is how you find the point where it stops being true on the hardware you are shipping to.

Reduced motion

0009's test was whether the movement is the message or the decoration. A wipe is an awkward case for it, because a wipe is not really movement — nothing translates — but it is a large area of the screen changing luminance on a schedule, which is exactly what the vestibular half of that audience is asking you to stop doing.

So the accommodation is not "make it shorter". It is to keep the reveal and drop the sweep: under prefers-reduced-motion: reduce, a masked entrance becomes an opacity fade of 80–120ms, or the element is simply present. The shape was carrying an idea about uncovering; a cross-fade gives up that idea, which is the correct trade, and shortening the wipe to 150ms does not — it just makes the sweep faster and harder to look at.

Both labs on this page take the stance the course has taken since 0009 and both say so in their source: the motion here is the content, so removing it leaves an empty page rather than a calmer one. Nothing autoplays, nothing loops, and every frame you have seen was the result of a press you made.

What you can now do

  1. Reveal something without moving it, and say out loud why that reads differently from a fade-and-rise rather than calling both "a reveal".
  2. Write an inset(), a circle() and a polygon() from the picture you want, including a radius on the window.
  3. Recognise the halfway-swap failure on sight, and know it is a values problem rather than a broken animation.
  4. Decide between a shape and a wrapper before writing either, with four questions and no benchmark.
  5. Measure the point where the shape stops being free, on the machine that matters.

A keyframe animation runs clip-path from inset(0 100% 0 0) to circle(70% at 50% 50%) over 600ms. What do you see?

Basic shapes interpolate only against their own type — inset to inset, circle to circle, polygon to polygon with a matching vertex count. Anything else is a discrete animation: hold, swap at 50%, hold. The animation genuinely exists and getAnimations() will show it, which is what tells you the values are the problem and not the mechanism.

A line of type has to be masked in from the left, must not move a single pixel while it does, and the window has to keep the card's 14px corners exactly where they are. Which build?

Two demands, and each wrapper build can only meet one of them. The moving window holds the type still, but its radius travels with it, so the corners sweep across the card. The static window keeps its radius exactly on the card, but the only thing that can move is the content, so the type slides. Both together is question 3 of the test, and a yes there buys the paint.

A feed of 200 cards, each wiping in from the left with a straight vertical edge as it scrolls into view. You reach for clip-path — one property, no wrapper, nothing added to the layout. What is wrong with the reasoning?

All four questions came back no — one straight edge, one moving edge, a wrapper you control, no radius conflict — so the rectangle could have done it. On one hero card the paint is unmeasurable and the habit is harmless; across 200 scrolling cards it is a bill you chose to be sent for nothing. Fewer nodes is a real argument, just not one worth a paint tier per card — and the measurement strip is there to tell you where your own machine draws that line.
