Lesson 0011 · 22 minutes

Layout animation

The first lesson where you don't author the animation. You measure it — twice — and let the difference between the two measurements be the animation.

Skill: animate a layout change you didn't write, and know when to hand it to the browser ← Lesson 0010

Everything in this course so far either appeared, disappeared, or moved on its own account. This one is about the third case: an element that was already on screen, is still on screen, and is now somewhere else.

Lesson 0002 sorted CSS properties by how far down the rendering pipeline they push you — layout, then paint, then composite — and the entire argument was to stay at the composite end. A card changing its position in a grid is a layout change by definition. So this looks like the one case where that budget simply cannot be met.

It can. You let layout happen — once, instantly, invisibly — and then you animate the pixels back. That inversion is the whole technique, and it has a name.

Try this, in order
  1. Press Shuffle a few times. Watch card 1, the outlined one.
  2. Set how the reorder is done to just change the DOM and shuffle again. That is what the browser does unaided.
  3. Back to FLIP. Press Step through it and read the four panels as they light up.
  4. Set the style flush to skipped and shuffle. One line of code is gone. Nothing else changed.
  5. Flush back to forced. Shuffle, and then shuffle again before it finishes.

First, Last, Invert, Play

The four letters are the four steps, and the lab's four panels are them in order.

First. Before you touch anything, ask every element where it is: getBoundingClientRect(). Store the rects.

Last. Make the change — reorder the DOM, add a class, remove a filter, whatever it is. Then measure again. The browser has already laid the new layout out; the elements are, at this instant, in their final positions. If you did nothing else, this is the jump you saw in step 2.

Invert. For each element, apply a transform that maps its new rect back onto its old one. translate(oldLeft - newLeft, oldTop - newTop). Now the screen looks exactly like it did before the change — but the DOM doesn't. The DOM is in its final state from Last onward. Only the pixels are lying.

Play. Remove the transform with a transition on it. The element travels to where it already is.

Count the layouts: one. It happens at Last, before anything is on screen that the user could see move. Every frame after that is a transform going to zero — the composite tier, the cheap end of 0002's pipeline. The layout change didn't get animated. It got hidden, and a composite-tier animation was played over the top of it.

This also explains something that would otherwise look like a coincidence: FLIP animates whatever caused the layout to change. The lab's shuffle and its filter are completely different operations — one reorders nodes, the other hides five of them — and the FLIP code doesn't know or care which one ran. It measured before and it measured after. That is the whole interface.

The word, so it isn't jargon later

Layout animation is the general name for this: an animation whose values are derived from two measured layouts rather than written by you. You never type a distance. You couldn't — the distance depends on the viewport width, the number of surviving cards, and where the shuffle happened to put things.

The one line that breaks it silently

Step 4 was the important one. Setting the flush to skipped removes exactly this:

void el.offsetWidth;

and the animation stops happening. Not "looks worse" — stops. No error, no warning, no console output. The cards teleport exactly as they did with FLIP switched off entirely.

Here is why. The browser batches style changes. Within one turn of the event loop it will happily collapse transform: translate(-329px, -66px) followed by transform: none into a single computed value — the last one — because that is the only value that would ever be painted. The inverted position never existed as a frame, so there is nothing to transition from.

Reading a layout property forces the browser to resolve styles now, mid-turn, to answer your question honestly. That resolution is what makes the inverted position real. Any layout read works — offsetWidth, offsetHeight, getBoundingClientRect(), getComputedStyle(el).transform. The void is only there to stop a linter complaining that you threw the value away.

This is the same forced synchronous layout that 0002 told you to avoid inside a loop, deliberately triggered once, on purpose. It is not a contradiction: layout thrashing is bad because it runs n times for n elements. Here it runs once for the whole batch, and it's the price of the technique.

The modern alternative is requestAnimationFrame(() => requestAnimationFrame(play)) — wait two frames instead of forcing one. It costs you a frame of latency. Both are correct; the flush is tighter and the double-rAF is easier to reason about in a framework that owns the render loop.

Why interrupting it works

Step 5: shuffling mid-flight doesn't snap. The cards pick up from wherever they visually are and re-route. That falls out of one fact that is easy to miss:

getBoundingClientRect() reports the box as painted — transforms included. A card that is 40% of the way through a FLIP measures at 40% of the way, not at the grid cell it is heading for. So First, on the second shuffle, captures the truth on screen rather than the truth in the layout, and the new invert is computed from there.

You get interruptibility for free, and you get it because the technique is built out of measurement rather than out of authored keyframes. There is no timeline to rewind. Compare 0008's springs, where interruptibility had to be designed in by carrying velocity across; here it is a consequence of asking the right question.

Two things the lab does not do, and you should know they are the hard parts:

  • It only translates. When a FLIP also changes size you need a scale in the invert, and a scaled box stretches everything inside it — text gets fat, border-radius goes oval. The standard fix is an inverse scale on a child wrapper, which is fiddly and is the reason people reach for a library here.
  • Nothing enters or leaves. An element with no First rect has no old position to come from, so a real implementation needs a separate entrance for it — which is 0003 and 0005, bolted onto the side of this.

Both of those are exactly what the browser now offers to do for you.

The browser will do all of this

Same idea, no measuring. You hand document.startViewTransition() a function that changes the DOM. The browser screenshots the page before your function runs, screenshots it again after, and animates between the two.

Try this, in order
  1. The mode starts at + a shared name. Click any tile, then Back to the grid.
  2. Switch to startViewTransition — same call, no names — and click a tile. Note what the browser does when it has no reason to think the two states are related.
  3. Switch to plain swap and click one. That is the baseline.
  4. Back to + a shared name. Set the names on the elements to all six the same and click a tile. Read the log.
  5. Names back to unique. Drag duration to 900ms and open a tile — slowly enough to see what is actually moving.

What the names are for

Without names you get a cross-fade, and that is the browser being honest: it has two pictures and no reason to believe anything in one corresponds to anything in the other.

view-transition-name supplies that reason. Give an element a name in the old state and give a different element the same name in the new state, and the browser treats them as one thing that moved and resized. It lifts each out of the page snapshot into its own layer, measures both rects, and animates between them.

Which is FLIP. Measure, measure, interpolate. The difference is that you didn't write it, and it's running on screenshots rather than on your live elements.

/* in CSS */
.tile.active, .detail-hero { view-transition-name: hero; }

// in JS
document.startViewTransition(() => {
  render(nextState);          // your normal DOM update
});

Two rules make the whole thing behave, and step 4 broke the second one:

  1. The name must be on the source element before the transition starts. Set it inside the callback and the old snapshot has nothing by that name, so there's nothing to morph from — you get a transition that runs, reports success, and looks like a cross-fade.
  2. A name must be unique in the document at capture time. Six tiles claiming hero is an error. The browser doesn't pick one, or animate the first — it throws the entire transition away, including the parts that were fine, and you get the hard cut. The log in the lab is the real rejection: InvalidStateError.

That second one is the production failure mode, and it is easy to hit for a boring reason: in a list, the obvious name is card, and then two cards are on screen at once. Names have to carry identity — card-42, not card.

Notice what the lab had to do to be embeddable: it gives its own stage a view-transition-name and then kills the animation on the root group. Without that, pressing a tile would dissolve this entire lesson page, because a view transition captures the whole document — always. There is no element-scoped version.

And the part that can't be opted out of: for the duration of the transition the page is a pair of screenshots. It doesn't scroll, it doesn't respond, and your animation cannot be interrupted — only skipped, with transition.skipTransition(). Hold the duration slider at 900ms and try to click something. That is the trade.

Where it runs

Same-document view transitions — document.startViewTransition(), view-transition-name, skipTransition() — are in Chrome and Edge since 111, Safari since 18, and Firefox since 144. MDN's own summary: "Baseline 2025 Newly available. Since October 2025, this feature works across the latest devices and browser versions."

Read that date carefully. It is recent enough that a real audience still contains browsers without it — which is fine, because the fallback is a hard cut and needs no feature detection. The DOM change in the callback happens either way.

Cross-document transitions — the CSS-only @view-transition { navigation: auto; } that animates between two separate HTML pages — are a different story: Chrome 126, Safari 18.2, and not supported in Firefox at all as of this writing. That's the headline feature in most of the demos you'll find, and it's the one you can't lean on yet.

Choosing between them

Now that you've felt both:

 FLIP, by handView Transitions
Who computes the movementYou, from two rectsThe browser, from two snapshots
What is animatingYour real elementsPictures of them, in a pseudo-element tree
ScopeExactly the elements you measuredThe whole document, always
InterruptibleYes — measure again mid-flightNo. Skip it and start over
Enter and exitYou write them separatelyIncluded, and stylable
Resizing without stretchingInverse-scale a child, by handIncluded
Across a page navigationNoYes — but not in Firefox yet
How it failsA silent jump (the missing flush)A silent cut (a duplicated name)
Where the code livesJSOne JS call, then CSS

The last row is the one that changes how a team works. Once the transition is started, every timing decision — duration, easing, which element moves and which fades — is a CSS rule on ::view-transition-group(), ::view-transition-old(), and ::view-transition-new(). Everything from lessons 0001 and 0002 applies to those pseudo-elements unchanged.

The rule

If the user can interrupt it, FLIP it. If it's over before they could, hand it to the browser.

A filter row someone hammers, a drag-to-reorder list, anything tracking a pointer — those need to be re-measurable mid-flight, and a frozen page is disqualifying. A route change, a thumbnail opening into a detail view, a theme swap — those are one-shot, the freeze is invisible at 300ms, and hand-rolling them means writing enter, exit, move, and the inverse-scale by hand.

Check yourself

How many times does layout run during a correct FLIP of 40 cards?

First reads the existing layout rather than causing a new one. The single layout at Last is the entire cost, and it happens before anything visible has moved. That's how a layout change gets animated on 0002's cheap tier.

You remove void el.offsetWidth; from a working FLIP. What happens?

Without a forced style resolution the invert and the play collapse into one computed value. The inverted position never existed as a frame, so there is nothing to transition from. No error is thrown, which is exactly what makes it hard to find.

Why can a FLIP be interrupted mid-flight without snapping?

The technique is built out of measurement, not out of an authored timeline, so there is nothing to rewind. Contrast 0008, where carrying velocity across an interruption had to be designed in deliberately.

Two visible cards end up with view-transition-name: card. What does the browser do?

It's an InvalidStateError and the entire transition is thrown away, including the parts that were correct. This is why names must carry identity: card-42, never card.

A filter row the user can click four times in two seconds. Which technique?

Interruptibility is the deciding axis. A view transition can only be skipped and restarted, and while it runs the page is a screenshot that doesn't respond. That's acceptable for a one-shot route change and disqualifying for a control someone hammers.

Read this next

Paul Lewis, "FLIP your animations" — the 2015 post that named the technique. Short, and the framing (invert the expensive thing rather than animating it) is the part worth keeping.

CSS-Tricks, "Animating Layouts with the FLIP Technique" — the practical write-up, including the scale-and-inverse-scale case this lesson only pointed at.

MDN, View Transition API and Chrome's same-document guide — MDN for the support tables and the pseudo-element tree, Chrome's for worked examples. Read the pseudo-element diagram before you try to style anything.

GSAP's Flip plugin and Motion's layout animations — both are FLIP with the hard parts done: nested inverse scaling, enter/exit, and shared-element transitions between components. In Motion it is one prop, layout. Now that you've hand-rolled it, that prop should read as a specific promise rather than magic — and 0006's ladder applies: reach for them when you need the scaling case, not before.
